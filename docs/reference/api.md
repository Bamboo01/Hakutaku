# API reference

Everything is JSON. IDs are generated by the server, so never send an `id`.

## Base URLs

| Where | Base URL |
|---|---|
| `dotnet watch` | `http://localhost:5008` |
| Vite dev server | `http://localhost:5173` (proxies `/api` to `:5008`) |
| Full Docker, locally | `http://localhost:8090` |
| Production, over the SSH tunnel | `http://localhost:8090` |
| Production, public | `https://51.79.242.169.nip.io` — **`/Health` and the player-auth routes only** (`register`, `login`, `link/email`, `email/verify`, `email/resend`, `password/forgot`, `password/reset`) |

!!! warning "Only these paths are publicly reachable"
    Caddy is default-deny. Every other path on the public domain returns `404`
    with an empty body, including the admin API. Use the
    [SSH tunnel](../operations/deploy.md#reaching-the-admin-ui).

## Authentication

There are two separate kinds of login, and a token from one is useless on the other.

**Admins** — every endpoint except `/Health`, `POST /api/admin/login` and the
player-auth routes needs a logged-in admin session cookie. `/api/admin/admins`
needs the **owner** specifically. The cookie (`hakutaku_admin_session`) is
`HttpOnly`, so a browser handles it automatically and JavaScript cannot read
it. With `curl` you need a cookie jar: `-c` to save, `-b` to send.

**Players** — `register` and `login` return a `token`. Send it back as
`Authorization: Bearer <token>`. A player token currently unlocks only
`link/email`, `email/verify` and `email/resend`; the rest of the game data is
still admin-only.

See [Auth and sessions](../components/auth.md) for the mechanics.

## Every endpoint

| Method | Path | Guard | Purpose |
|---|---|---|---|
| GET | `/Health` | — | Liveness check |
| POST | `/api/admin/login` | Rate-limited | Sign in, sets the session cookie |
| POST | `/api/admin/logout` | Session | Revoke the session, clear the cookie |
| GET | `/api/admin/me` | Session | Who the current cookie belongs to |
| GET | `/api/admin/admins` | **Owner** | List all admins, including deactivated |
| POST | `/api/admin/admins` | **Owner** | Create an admin |
| DELETE | `/api/admin/admins/{id}` | **Owner** | Deactivate an admin |
| POST | `/api/players/register` | Rate-limited, **public** | Find-or-create a player by device ID, returns a session token |
| POST | `/api/players/link/email` | Player token, **public** | Add an email + password to the current player |
| POST | `/api/players/login` | Rate-limited, **public** | Sign in with email + password, returns a session token |
| POST | `/api/players/email/verify` | Player token, rate-limited | Confirm the emailed 6-digit code |
| POST | `/api/players/email/resend` | Player token, rate-limited | Mail a new verification code |
| POST | `/api/players/password/forgot` | Rate-limited, **public** | Mail a password-reset code |
| POST | `/api/players/password/reset` | Rate-limited, **public** | Set a new password with the code |
| GET | `/api/players` | Admin | List all players (id, xp, linked providers) |
| POST | `/api/players` | Admin | Create a player |
| GET | `/api/characters` | Admin | List all characters |
| POST | `/api/characters` | Admin | Create a character |
| GET | `/api/events` | Admin | List all telemetry events |
| POST | `/api/events` | Admin | Record a telemetry event |

There is **no `PUT` and no `DELETE`** on game data, and list endpoints return
the entire table — no paging, no filtering.

!!! info "Planned changes"
    The game-data paths are intended to become **singular** (`/api/players` →
    `/api/player`). Characters and events will open to player tokens once the
    player API is designed. `player_bans` does not exist yet.

## Admin: sign in

```bash
curl -c cookies.txt -X POST http://localhost:5008/api/admin/login \
  -H "Content-Type: application/json" \
  -d '{"username":"admin","password":"<password>"}'
# 204, Set-Cookie: hakutaku_admin_session=...
```

**Body:** `username` (string), `password` (string).

Login is by **username**, not email. Matching is case-insensitive and the
username is trimmed.

| Status | When | Body |
|---|---|---|
| `204` | Success | **Empty** — the cookie is in the header |
| `400` | Missing field, or username > 254 / password > 256 chars | `{ "error": "username and password are required" }` |
| `401` | Wrong password, unknown username, **or disabled account** | `{ "error": "invalid credentials" }` |
| `429` | More than 5 attempts per minute from one IP | **Empty body** |

!!! warning "Two client traps here"
    `204` means `res.json()` throws — there is no body to parse. And `429` is the
    only error status without an `{ error }` body, because it comes from the
    framework's rate limiter rather than from handler code.

All three failure cases return the same `401` on purpose, so the API does not
reveal which usernames exist.

## Admin: who am I

```bash
curl -b cookies.txt http://localhost:5008/api/admin/me
# {"username":"admin","email":null,"role":"owner"}
```

`role` is `"owner"` or `"admin"`. Nothing else is possible.

This is how a front end discovers whether its cookie is still good without
asking for a password again. `401` if there is no cookie, or the session has
expired or been revoked.

!!! danger "Never call this on a timer"
    It is an authenticated request, so it pushes the 30-minute idle expiry
    forward. Polling it means the idle timeout can never fire. Call it on app
    load and on route changes.

## Admin: sign out

```bash
curl -b cookies.txt -X POST http://localhost:5008/api/admin/logout
# 204, clears the cookie
```

Returns `401` if you were not logged in. Treat that as "already logged out"
rather than an error.

## Admin: list admins

```bash
curl -b cookies.txt http://localhost:5008/api/admin/admins
```

```json
[
  { "id": 1, "username": "admin", "role": "owner",
    "createdAt": "2026-09-25T09:52:16Z", "disabledAt": null },
  { "id": 5, "username": "bob", "role": "admin",
    "createdAt": "2026-10-01T04:10:00Z", "disabledAt": "2026-10-01T05:00:00Z" }
]
```

Owner only. **Includes deactivated admins** — `disabledAt` is non-null for
those — so the UI can show state and target a deactivation.

Ordered by `id`.

## Admin: create an admin

```bash
curl -b cookies.txt -X POST http://localhost:5008/api/admin/admins \
  -H "Content-Type: application/json" \
  -d '{"username":"bob","password":"a-real-password"}'
# 200 {"id":5,"username":"bob","role":"admin"}
```

**Body:** `username` (string, ≤ 254), `password` (string, 8–256).

Always creates a **regular admin**. There is exactly one owner — seeded at first
start — and this endpoint cannot create another.

| Status | When |
|---|---|
| `200` | Created |
| `400` | Missing username, or password outside 8–256 characters |
| `401` | Not logged in |
| `403` | Logged in as a non-owner admin — `{ "error": "owner only" }` |
| `409` | Username already taken (case-insensitively) |

## Admin: deactivate an admin

```bash
curl -b cookies.txt -X DELETE http://localhost:5008/api/admin/admins/5
# 204
```

Sets `disabled_at` and immediately revokes that admin's active sessions. Does
**not** hard-delete the row, and there is no restore endpoint.

| Status | When |
|---|---|
| `204` | Deactivated |
| `401` | Not logged in |
| `403` | Not the owner, **or the target is the owner** |
| `404` | No such admin |

!!! danger "One-way, and it burns the username"
    The unique index on `lower(username)` covers disabled rows, so that username
    can never be reused.

    The **owner account can never be deactivated**, whoever asks. The seeder
    only runs when there are zero admins, so disabling the sole owner would lock
    everyone out with no HTTP way back in.

## Game data

Characters and events still need an admin session. The player-auth routes do
not — see below. IDs are GUIDs — **treat them as opaque strings**; do not
parse or format them.

### Player registration

```bash
curl -X POST http://localhost:5008/api/players/register \
  -H "Content-Type: application/json" \
  -d '{"deviceId":"some-device-id"}'
# {"id":"<player-id>","deviceId":"some-device-id","xp":0,"token":"<token>","expiresAt":"..."}
```

No cookie needed. **Find-or-create**: calling it again with the same
`deviceId` returns the same player, not a new one. The device ID is stored as a
`player_identities` row whose key is `(provider, subject)`, so even two
near-simultaneous calls for a brand-new device can't create duplicate players.

**Every call returns a new session token** (valid 30 days), even for an
existing player. Only a hash of the token is stored, so it can't be handed out
twice. Old tokens keep working until they expire.

| Status | When |
|---|---|
| `200` | The player and a fresh token |
| `400` | Missing or empty `deviceId`, or over 254 characters |
| `429` | More than 5 attempts per minute from one IP |

!!! warning "The device ID is a credential"
    The game generates it and keeps it on the device. Anyone who learns it can
    register with it and get a session as that player. Treat it like a password.

### Link an email

```bash
curl -X POST http://localhost:5008/api/players/link/email \
  -H "Authorization: Bearer <token>" -H "Content-Type: application/json" \
  -d '{"email":"player@example.com","password":"at-least-8-chars"}'
# {"provider":"email","email":"player@example.com","verified":false,"verificationSent":true}
```

Adds an email + password to the player the token belongs to. The device
identity stays, so the same device can still register. The email is trimmed and
lowercased. The password must be 8–256 characters.

The email starts **unverified**, and a 6-digit code is mailed to it
(`verificationSent` says whether that worked; if not, use `email/resend`). The
link itself is saved either way, and login works before verifying. Only a
verified email can reset its password.

| Status | When |
|---|---|
| `200` | Linked |
| `400` | Not a plausible email, or the password is the wrong length |
| `401` | Missing, unknown, revoked or expired token |
| `409` | This player already has an email, **or** that email belongs to someone else |

!!! warning "An unverified email can still be claimed"
    Until someone verifies it, an address is only a claim. A player who links
    someone else's address blocks the real owner from linking it (`409`) until
    that happens. Nothing cleans up unverified claims yet.

### Verify an email

```bash
curl -X POST http://localhost:5008/api/players/email/verify \
  -H "Authorization: Bearer <token>" -H "Content-Type: application/json" \
  -d '{"code":"123456"}'
# {"verified":true}

curl -X POST http://localhost:5008/api/players/email/resend \
  -H "Authorization: Bearer <token>"
# {"sent":true}
```

Codes are 6 digits, valid for **15 minutes**, single use, and die after **5
wrong guesses**. A newer code replaces the older one.

| `verify` status | When |
|---|---|
| `200` | Verified (also if it already was) |
| `400` | Wrong, expired, used-up or malformed code, or no email linked |
| `401` | Missing or bad token |
| `429` | Over the 5 per minute per IP limit |

| `resend` status | When |
|---|---|
| `200` | A new code was mailed |
| `409` | Already verified |
| `429` | A code was sent in the last 60 seconds, or over the per-IP limit |
| `503` | The mail server refused or failed |

### Forgot and reset a password

```bash
curl -X POST http://localhost:5008/api/players/password/forgot \
  -H "Content-Type: application/json" -d '{"email":"player@example.com"}'
# {"ok":true}

curl -X POST http://localhost:5008/api/players/password/reset \
  -H "Content-Type: application/json" \
  -d '{"email":"player@example.com","code":"123456","newPassword":"a-new-password"}'
# {"ok":true}
```

`forgot` answers `200` **whether or not** that email has an account, so it can't
be used to find out who does. A code is only mailed for a *verified* email, at
most once a minute per player. The code works like a verification code.

`reset` sets the new password (8–256 characters) and **revokes every session**
the player has. It does not log them in; they sign in again with `login`, or
`register` with the device ID.

| `reset` status | When |
|---|---|
| `200` | Password changed |
| `400` | Wrong, expired or used-up code, unknown or unverified email, or a bad password length |
| `429` | Over the 5 per minute per IP limit |

!!! note "Without an SMTP server nothing is mailed"
    If `SMTP_HOST` is not set, the app writes the message, code included, to its
    log instead. That is how the local setup works. See
    [Auth and sessions](../components/auth.md#email-codes).

### Email login

```bash
curl -X POST http://localhost:5008/api/players/login \
  -H "Content-Type: application/json" \
  -d '{"email":"player@example.com","password":"at-least-8-chars"}'
# {"id":"<player-id>","xp":0,"token":"<token>","expiresAt":"..."}
```

| Status | When |
|---|---|
| `200` | The player and a fresh token |
| `400` | Missing or malformed email, or missing password |
| `401` | Wrong password **or** unknown email — identical body, so it can't be used to find out which emails exist |
| `429` | More than 5 attempts per minute from one IP |

### Request bodies (admin-gated endpoints)

| Endpoint | Fields |
|---|---|
| `POST /api/players` | `xp` (integer), optional `deviceId` (string). Without a `deviceId` the player has no way to sign in. `409` if the device ID is taken |
| `POST /api/characters` | `playerId` (GUID of an existing player), `name` (string) |
| `POST /api/events` | `playerId` (GUID of an existing player), `eventType` (string), `data` (string holding JSON text) |

`timestamp` on an event is always set by the server in UTC. Anything you send
for it is overwritten.

Responses echo the created object. Character and event responses also include
`"player": null`, which you can ignore — it is an unpopulated navigation
property.

### Worked example

```bash
curl -b cookies.txt -X POST http://localhost:5008/api/players \
  -H "Content-Type: application/json" \
  -d '{"deviceId":"device-1","xp":0}'
# {"id":"<player-id>","xp":0}

curl -b cookies.txt -X POST http://localhost:5008/api/characters \
  -H "Content-Type: application/json" \
  -d '{"playerId":"<player-id>","name":"Hero"}'

curl -b cookies.txt -X POST http://localhost:5008/api/events \
  -H "Content-Type: application/json" \
  -d '{"playerId":"<player-id>","eventType":"level_up","data":"{\"level\":2}"}'
```

## Error shapes

Four different shapes, and a client has to handle all of them:

| Shape | Which responses |
|---|---|
| `{ "error": "message" }` | `400`, `401`, `403`, `404`, `409` |
| Empty body | `204` (success), and `429` |
| Bare `500` | A `playerId` that does not exist — an uncaught foreign-key violation |
| `404` with empty body, `Server: Caddy` | Caddy's default-deny, not the app at all |

`web/src/api.ts` is a working reference for handling these in one place.

!!! note "Malformed JSON returns `400`"
    From the framework's model binding, before any handler runs.

## What does not exist

Asked for often enough to be worth listing:

| Wanted | Status |
|---|---|
| `GET /api/players/{id}` | **No** — list endpoints only |
| Filtering a player's characters or events | **No** |
| Paging | **No** — every list returns the whole table |
| `PUT` / `PATCH` / `DELETE` on game data | **No** |
| Player logout / revoking a player session | **No** — tokens last 30 days |
| Player access to characters and events | **No** — a player token only unlocks the email routes |
| Unlinking or changing an email, changing a password while signed in | **No** |
| Server keys for game servers | **No** — blocks the [simulator](../components/simulator.md) |
| Game-server endpoints | **No entity exists** |
| An audit log | **No table exists** |
| Admin password change / reset | **No** (players have a reset by email) |
| Restoring a deactivated admin | **No**, by design |
